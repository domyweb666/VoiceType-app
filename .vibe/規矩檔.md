# 規矩檔（AI 每次動工前必讀）

## 通用 AI 行為基準（從專案第一天起就成立，勿改）

1. **不准猜假設，不確定就問。** 收到任何指令，若有不明確的詞、有多種可能的解讀、缺少關鍵資訊——**停下來把不明確的地方列出來問使用者**，不要替他選一個解讀就動手。靜默的假設是這套系統最大的失敗源頭。

2. **每一行改動都必須能追溯到使用者的明確要求。** 不准順手「改進」相鄰的程式碼、不准重整不相干的格式、不准刪掉「看起來像死碼」但不在這次任務範圍內的東西、不准做沒被要求的重構。每一行 diff 都要對得上一句使用者講過的話。
   - **（刻意反「童子軍原則」，重要）**：工程界有條「童子軍原則／破窗效應」——路過爛 code 順手修乾淨。**這套系統故意不這樣做**：對看不懂程式碼的人，「順手清理」是**驗不到的暗改**，一個 drive-by「整理」可能靜默弄壞別處而他永遠看不到。所以**破窗要修，但要用一片正式的 `vibe-simplify`（走過審核）去修，不准路過時即興順手改**。清理是一個被切出來、驗得到的動作，不是夾帶在別的任務裡的副作用。

3. **不准加沒被要求的功能、抽象、設定項。** 「想說以後可能會用到」「順便寫得更彈性一點」「加個 config 比較好」——全部不准。要做的事跟使用者要的事一對一，多的一律砍。（注意：這條禁的是替想像情況**鍍金**；下面第 4 條的健壯性地板是**最低要求**，不在此限。）

4. **錯誤要大聲、輸入要驗、爆了要倒向安全側（健壯性地板）。** AI 寫的程式表面會跑，但**邊界與錯誤處理常常是空的**——而看不懂程式碼的人看不到空的 catch、看不到沒驗證的輸入。這四條是地板，寫任何程式一律遵守（這不是第 3 條禁的「鍍金」：錯誤一定會發生，差別只在「大聲報」還是「默默吞」）：
   - **快速失敗、不准默默吞**：一發現不對就大聲報錯停下，**不准用空的 catch 把錯誤吃掉繼續跑**。吞掉的錯不會消失，只會用更難懂的形式在更遠的地方爆。
   - **外部進來的一律先驗證**：使用者輸入、API 回傳、檔案內容——用之前先檢查，絕不假設它是好的（這同時是健壯性與安全的根）。
   - **爆掉時倒向「拒絕／鎖住」，不是「放行」**：尤其權限／付費／安全相關，出錯的預設是「不准」，不是「那就讓他過吧」。
   - **保護式子句**：不合法的狀況在函式開頭就擋掉提早 return，讓正常路徑保持平坦，不要把主邏輯埋在層層巢狀 if 裡。

## 專案特定規矩（vibe-voice-lock 之後寫入這下面）

> 2026-10-31 由 vibe-voice-lock → vibe-constitution 產出。這一區約束 AI 的「判斷」。
> 格式與可用工具驗證的規則不寫在這裡，交給 `ios-native/.swiftformat`、`ios-native/.swiftlint.yml`（CI 強制）與 `.vibe/hooks/pre-commit`（每次 commit 強制）。
> 語言：Swift＋SwiftUI，程式只放 `ios-native/`。Flutter 舊碼是參考，不改。

### 0. 前提
- 格式不用管，SwiftFormat 會處理；不要為排版花任何推理。
- 寫程式前先讀 `ios-native/` 裡鄰近的檔案，模仿既有結構；沒有鄰近檔案時用最少的程式碼。
- 寫畫面一律用 `.uiux/05-設計代號/Tokens.swift` 的代號，不准手寫顏色、字級、圓角數字；文案照 `.uiux/05-設計代號/詞彙表.md`。

### 1. 架構邊界（照藍圖的方塊切資料夾，不照技術分層）
- 資料夾對應藍圖方塊，一個方塊一個資料夾：`Recording`（M1）、`PendingQueue`（M2）、`Transcription`（M3）、`Polishing`（M4）、`Storage`（M5）、`APIKey`（M6）、`Settings`（M7）、`Backup`（M8）、`Screens`（M9，依畫面再分）、`OpenAI`（M11）；`App/` 放進入點與 `Tokens.swift`。不准開 `Utils/`、`Helpers/`、`Managers/`、`Common/` 這類技術分層資料夾。
- 方塊之間只透過藍圖「用到誰」那一欄允許的方向呼叫；藍圖沒畫的依賴不准加，要加先回去改藍圖。
- 不准引入 Coordinator、VIPER、Clean Architecture、Redux／TCA 這類架構；畫面用 SwiftUI 的 `@State`／`@Observable`，最多一個薄的 view model。
- 不准為單一型別先抽 protocol；要有第二個實作（例如測試用的假 OpenAI）才抽，而且只抽那一個。
- 不准 protocol＋associatedtype 的泛型體操。
- 不准沒理由就把同步邏輯包成 async 或 Combine；只有真的等網路、等檔案、等錄音時才用 async/await。不用 Combine。
- 架構分界先用資料夾；等到方塊超過三個檔案互相引用時，再問米要不要切 SPM module。

### 2. 反過度工程禁令（逐條皆為可判定動作）
- 不准為「未來可能會用到」加參數、抽象層、config 開關、feature flag。YAGNI 寫死。
- 新功能預設寫成一個函式或一個 struct。要拆檔案、拆型別、引入抽象前，先停下來問米。
- 不准引入任何切片標準沒指定的第三方套件。OpenAI 直接用 `URLSession`，不裝 SDK；加密用 CryptoKit；儲存用檔案系統＋Codable，不裝資料庫套件。要加套件先問米，加了只准用 Swift Package Manager 並鎖定版本。
- 不准自己寫 Keychain 包裝以外的「通用儲存層」、「通用網路層」、「事件匯流排」。
- 不准加「以防萬一」的重試、快取、背景工作；重試規則只准照 PRD 與安全標準寫的次數與時機。
- 不准留下 `TODO`、`FIXME` 進 commit；做不完就寫進切片帳本。

### 3. 健壯性地板（第 4 條通用基準在 Swift 裡長這樣）
- 不准 `try!`、`as!`、`fatalError` 當錯誤處理（只有程式邏輯不可能走到的分支才准 `fatalError`，而且要寫為什麼）。
- 不准空的 `catch {}`、不准 `try?` 吞掉會影響資料的錯誤。錯誤一律往上拋成有意義的 `enum ...Error: Error`，讓畫面能照詞彙表講人話。
- 不准 `print`、`NSLog`、`debugPrint`。要記錄用 `os.Logger`，而且**金鑰、錄音內容、口語稿、文字稿一律不准進 log**，連遮一半都不准。
- 外部進來的一律先驗：OpenAI 回應先驗 HTTP 狀態與 JSON 結構；匯入的檔案先驗格式與大小；使用者輸入的金鑰先 trim 再存。
- 刪檔只准在「新資料已寫成功」的那一行之後；寫檔用原子寫入（先寫暫存檔再 rename）。
- 任何錯誤的預設結局是「停下、保留資料、告訴使用者」，不是「跳過繼續」。

### 4. 可讀性鐵則（AI 下次用更少脈絡讀懂自己的專案）
- 命名要表達意圖：`elapsedSeconds` 不是 `t`，`pendingRecordings` 不是 `list`，`isPolishing` 不是 `flag`。照 Swift API Design Guidelines：型別大駝峰、其餘小駝峰、布林用 `is`／`has`／`can` 開頭。
- 註解只寫「為什麼」，不寫「做什麼」：記當下的取捨、踩過的雷、不得不的妥協；不准寫 `// 取得使用者` 這種複述程式碼的註解。
- 不留魔術數字：`10 * 60` 要叫 `segmentDurationSeconds`，`4` 要叫 `maxTranscriptionRetries`，放在用到它的那個型別裡的 `static let`。
- 最小驚訝：函式不准做名字沒說的事。`load()` 不准順手刪壞檔，`save()` 不准順手複製到剪貼簿；副作用要寫進名字或拆成另一個函式。
- 一個檔案一個主要型別，檔名等於型別名。

### 5. AI 行為準則
- 改既有的，不要新增：優先修改現有的型別與函式，而不是另開一個平行的。
- 動手前先掃 `ios-native/` 有沒有已經做過的東西，不重複造工具函式。
- 每片只動切片帳本「本片動到的檔」那一欄列的檔案；要動別的檔先回去改計畫讀稿。
- 寫完一片先過 `.vibe/安全標準.md`，🔴 項沒做到不准說做完。

### 6. 不確定時
- 選最無聊、最少程式碼、最像鄰近檔案的做法，然後問米。
- OpenAI 的模型名稱、端點、價格、檔案大小上限、iOS API 的可用版本：寫程式前查證，不憑記憶。

### 這套規矩怎麼被強制（米不用做、不用看）
- **每次 commit**：`.vibe/hooks/pre-commit` 掃暫存區，擋金鑰與憑證、本機絕對路徑、`print`／`NSLog`、`try!`／`as!`、空 `catch`、`http://`、關掉 ATS 的設定、`TODO`。擋到就 commit 不進去。
- **每次推上 GitHub**：A1 的工作流程跑 `swiftformat --lint` 與 `swiftlint --strict`，不過就紅燈。
- 新 clone 要跑一次：`git config core.hooksPath .vibe/hooks`

## 安全標準（vibe-security-gate 階段 A 之後在這裡掛載連結）

- 專案類型：Mobile App（iOS，SwiftUI）＋ 有調用 LLM（OpenAI）
- 適用標準：OWASP MASVS、OWASP Top 10 for LLM Applications
- 完整清單見 `.vibe/安全標準.md`；每寫完一個功能先過清單，🔴 項沒做到不准過驗收
- repo 是 public：金鑰、憑證、密碼、Apple ID 信箱、本機絕對路徑一律不准進 repo
- 上線前必跑：vibe-security-gate（階段 C）

## 踩過的坑・不准再犯（vibe-no-repeat-error 自動回灌）

- 不要依賴 GitHub runner 映像「預裝」的工具（因為 2026-10-31 README 寫 SwiftLint 預裝，macos-26 實際沒有，CI 紅一次）。CI 用的工具一律從官方 release 下載、釘版本、驗 SHA-256，照 `ios-native-ci.yml` 裡 XcodeGen 與 SwiftLint 的寫法。
- Swift 宣告（型別、函式、屬性）上方的註解用 `///`，函式體內用 `//`（因為 2026-10-31 SwiftFormat 的 docComments 規則讓 A1 紅一次）。
- 寫完一片，推上去前先對標準清單「絕對不准做」逐條掃 diff，再對每一行問「哪句話要我加這個」（因為 2026-10-31 A1 自審抓到寫死 Xcode 路徑與七個沒被要求的 project.yml 鍵）。
